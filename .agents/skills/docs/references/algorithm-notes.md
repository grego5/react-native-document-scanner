# Algorithm notes and measurements

Read only the section relevant to an algorithm change. [Architecture](architecture.md) holds ownership and public contracts; code holds current constants. Measurements below are historical evidence on the stated fixtures/device, not general performance guarantees. Validation procedures are in [Development](development.md).

## Image processing

- Photo detection decodes only its input region, at half resolution: the model reads 224 px, and full resolution doubled detection time on the SM-G998U (decode and tensor resize; inference stays about 8 ms).
- Rendering decodes only the corners's bounds plus 10% per side (PageEdges searches 6%) at full resolution, up to 4096 px. The margin never reaches the output: the warp targets the export size, and shadows/filters run on that canvas.
- Live detection runs one full-image inference; photo analysis runs one inference on its selected region. Live results are accepted immediately; adaptive inference can pause on the next reliably tracked frame. There is no pending live crop or second live inference. The photo region is the shutter guide's bounds plus at least 10% per side, grown toward a square within the photo so the square tensor stretches it least; without a valid guide, the whole photo. Predictions map back to the full upright photo. A badly wrong guide can crop the page off; that is a live-model failure, not a reason to widen the margin. The guide still seeds the initial crop preview. Both selected inputs use the existing square tensor resize; analysis requests 640x480 and the bundled model input is 224x224.
- The drawn guide eases toward each accepted outline with an exponential whose time constant falls with the gap, as the One Euro filter adapts to speed: 80 ms (`guideTransitionDuration`) up to a twentieth of the snap distance, so jitter barely moves it, falling to 20 ms by half of it, so it keeps up with a moving page; a corner farther than the snap distance (a fifth of the view's diagonal) snaps. It replaced a fixed 50 ms linear ease, which passed jitter through in full; the constants are not yet tuned on a device.
- Filters even the lighting with one paper-brightness estimate that divides every channel: per-channel division turned a broad pastel patch white. `blackWhite` is a continuous curve, not a threshold, because thresholding discarded faint strokes. Filter constants are starting points, not tuned on a range of real pages.
- After evening, `InkDetail` deepens faded thin ink and sharpens soft areas per tile (8 across the short side), since glare and distance from the lens leave parts of a page with weaker ink and softer edges. Ink depth is a black-hat about a text line wide, kept per pixel, and only that depth is deepened, so a gray box sharing a tile with faded text keeps its tone. Text-free tiles borrow their neighbours' values; sharpness is relative to the tile's depth, so it reflects blur alone. Both fold into the unsharp mask x + a × (x − blur) − (s − 1) × ink.
- Passes that apply a small map per pixel run natively (`FieldKernels`): the ink pass, shadow removal's gain, and the divide by the paper, which also applies the white balance (in the gray weights for the gray filters). Each map is enlarged a row at a time as `Imgproc.resize` with INTER_LINEAR would; rows run in parallel, 16 pixels at a time, in the float order of the OpenCV passes they replaced and without fused multiply-add, so output matches within one level. On the SM-G998U, for a 4096x3072 page, the ink pass fell from about 77 to 16 ms and the gain from 65 to 9 ms; `enhance` takes about 210-230 ms, `grayscale` and `blackWhite` 160-190 ms, shadow removal 35-130 ms. `RenderTimingTest` (`-e measure true`) times the stages.
- Renders and filter previews run in `FastCores.run`, which pins the calling thread and OpenCV's workers, by thread id, to the cores the kernel's `cpu_capacity` rates at least half the fastest (or at 70% of the top clock where none is exposed), and releases them after the last overlapping call, since the workers serve the camera too. After an idle pause, as between captures, the scheduler left much of a render on slow cores: on the SM-G998U its median fell from about 340 to 255 ms on the four big cores, faster than the mid or prime cores alone. It pins anew on every call, as backgrounding resets affinity, and does nothing where no core is markedly slower. Performance hint sessions are unavailable there, and the public API has no hint for a one-off burst.
- Corner inference, live and photo, runs on one interpreter thread that pins itself to the prime cores, those rated as the fastest, before every task (`FastCores.prime`), with one TFLite thread. On the SM-G998U a warm inference takes 9.4 ms on any thread count, rising to about 33 ms after 300 ms idle as clocks drop; in live preview, inference with frame preparation took a median 24 ms pinned against 29 ms left to the scheduler, which spread it over the big cores, and 24 against 32 ms after a pause. Optical flow stays unpinned on the analysis thread.
- Monochrome PNG output is 4-bit gray, so gray text edges survive. There is no 1-bit output.

- Bent edges (`simpleDewarp`, on by default; `PageEdges`): on an 800 px rectified copy with a 6% band, 31 stations per side take the strongest colour step, and t(1 - t)(a + bt + ct²), pinned at the corners, is fitted by a search over station triples then least squares (a + bt alone missed printer pages near their corners). A side bends only when at least 16 stations agree within 1.5 px, the agreeing stations reach both corners (so a printed rule mid-side cannot pair with the paper edge), the bend lies between 1.5 px (smaller ones were wavy flat edges) and the band, and the edge stays in the photo. Sides join by a Coons patch before the inverse homography. `validContentPolygon` comes from the straight warp, so bending is skipped when a corner lies outside the photo. The map is built natively (`PageEdgesRemap`, -O2 in debug too) a 128-row strip at a time and resampled with `remap`: on the SM-G998U edges take 25-38 ms and the curved warp 31 ms against 18 ms straight, where building the map in Kotlin or with OpenCV calls took 110-125 ms.

- Shadow removal (`removeShadows`, on by default) runs on the warped page before the filter, so the filter's own paper estimate sees even light; run after it, the shadow had already been flattened and toned. It replaced an SCI low-light model with soft and hard modes: SCI's 258-weight estimate read dense text and printed photos as shade, Soft left moderately shaded areas half corrected, and its colour matching was a second heuristic on top. The estimate now closes ink away (a square 2.5% of the reduced short side) on the brightest channel of a copy at most 512 px long, since ink keeps one bright channel and shade darkens all three, then lifts toward the 90th percentile, capped at 2x. On a page with a hard sun shadow, the filters without it left a blue patch (`enhance`) or a grey half (`grayscale`, `blackWhite`); with it first, all three came out evenly white. A guided enlargement of the gain looked the same there, so the gain is enlarged bilinearly. Areas wider than the closing kernel and darker than paper, such as fingers, are lifted too.

## Capture quality

- Optical flow judges blur; the gyroscope is the fallback. In recorded A4 scenes the gyro flagged sharp OIS-stabilized frames as blurred, while flow ignores rotation that OIS cancels and also sees translation and approach. Twelve captures split at 0.2%: steady ones had at most 0.09% flow blur, moving ones at least 0.31%.
- There is no age limit on frame results: the newest one is the latest knowledge there is, and a fixed limit only rejected good results from slow inference. Analysis writes a record for every frame it receives, so records go old only when analysis stalls, such as while the model loads. A capture approved, after a focus or torch change, on a record an earlier evaluation already read logs its age. Missing flow is unknown, never steady.
- Flow speed is the fastest page region, so one waving region decides.
- Zero shutter lag only saves a frame from CameraX's buffer if that frame reported AF focused (locked or passive), AE converged and AWB converged; otherwise CameraX quietly takes a new picture. Photographing a 240 Hz counter showed both: with the page already locked the photo was a buffered frame about 60 ms before the shutter, while a capture that had just waited for focus saved a new frame about 340 ms after it, which caught a shake the motion check had passed. Supported autofocus ZSL captures therefore wait until the newest judged frame reports those three states. The buffer drops frames that fail those states without evicting older ones, and returns its newest frame however old: in a dim room on the SM-G998U, a shot after a two-second focus scan returned a blurred frame from before the scan, or the background from before the page came into view. A capture therefore never shoots zero shutter lag without that readiness; it rejects at the deadline.
- Capture checks complete frame analysis results rather than separately updated values. The analyzer records one `FrameRecord` per analyzed frame: that frame's own capture result (AF, AE and AWB states, exposure), its flow from the previous analyzed frame, its motion blur and source (flow over its exposure, else the gyroscope), calculated once and shared with analysis and traces, the gyroscope's speed over the flow interval, and the confirmed in-frame guide after it. Capture reads them in order from a bounded `FrameHistory`, each once, so a busy main thread delays evaluation without losing frame results; a reader more than 32 frames behind is told so and restarts its sequence. Only frames exposed after the latest focus change count. A frame whose capture result had not arrived when analysis started is looked up again when it is recorded; one still without it keeps the sequence through it, checking speed and the page, but does not count. While focus is required, a frame that reports focus lost restarts the sequence.
- Three checks decide whether a frame continues the stable frame sequence, since they answer different questions: framing (flow under 5% of the frame width per second, whatever the exposure, with gyroscope speed where texture is too sparse for flow), motion blur (the frame's own blur within `captureBlurPercent`), and with `guideLiveCorners` the page's drift from the sequence's first frame (position 2%, scale 3%, shape 2% of corner travel). Four consecutive analyzed frames must pass, and the sequence must reach the newest frame. Missing, broken or non-consecutive flow, unknown motion blur or a missing page restart it. The thresholds are starting settings from the recorded split below 0.09% and above 0.31% blur at a typical 30 ms exposure.
- One `CaptureGate` per capture owns readiness, its own focus scans and both deadlines, and returns start a focus scan, wait (with its reason), shoot or reject; hints come from the reason. The view gathers observations into `CaptureState` (separate ZSL and light readiness, the scan trigger, the capture's scan state, movement during it) and executes the decision; `FocusController` runs the scan. ZSL readiness stays required when optional focus is skipped, since the buffer would return an older frame; light readiness (no pending torch or boost change) too. Focus, with its page under `guideLiveCorners`, waits up to 4 s; once it holds, everything must align within 1 s, since light and steadiness take tens of milliseconds once focus has settled, and losing focus later waits within that same deadline. Autofocus still moving, a scan or continuous autofocus searching, extends a focus wait past either deadline, so a shot never fires or fails halfway through focusing; only autofocus that settled without focus fails. The page has no such extension, except while the capture's own scan runs (see Scans). Without `requireFocus` focus is not waited for, and the page deadline shoots instead of rejecting, but never bypasses ZSL readiness, light or steadiness. A lost page or lock reports `capture/focus-timeout`, exposure, white balance or a torch change `capture/failed`, motion `capture/motion-timeout`. The gate is evaluated on events (new frames, a focus or torch change, its deadline), never on a polling timer, and the first evaluation where all conditions pass starts capture, with no settling delay. Hardware-dependent choices, such as whether zero shutter lag applies, read the configuration the camera was bound with, not props changed since. CameraX still picks the buffered frame, so the photo approximates the approved frame sequence; the lifecycle log records each still's sensor time against the shutter. A capture takes one shot.
- With `guideLiveCorners` a capture waits for a page, then for focus as Document focus describes, within the gate's focus wait above. Fixed-focus cameras, detected from AF modes because Android may omit the minimum focus distance, need a page but no focus.

## Torch

- Auto decides from the exposure time and ISO that auto-exposure already reports for every frame, so it needs no pixel work. Their product grows as light falls; the dark threshold and one-second wait are starting settings, and the stats strip shows the live product for calibration.
- Once lit, auto stays lit until the camera stops or the mode changes. A lit torch brightens the page, so exposure no longer shows the room's own light, and switching off to look would flicker.
- Auto does not use Camera2's flash-required AE state: that needs auto-flash AE mode, which also fires the flash for stills and disables zero shutter lag.
- `CameraLightController` owns the torch and boost commands, their CameraX confirmations, their deferral and the light fallback below. Neither changes while a capture is pending, since CameraX turns the torch off when the boost goes on; the capture's end sends the latest wish. CameraX confirms a change asynchronously, so a photo also waits for one sent just before the press. Unbinding retires every request, so a late completion publishes nothing.
- Low-light boost (`lowLightBoost`, on by default, Android only) asks CameraX for the camera's own boost mode, which the camera engages only when dark. It is off whenever the torch mode is not `off`, and the boost goes off before a torch lights. It was added after continuous autofocus on the SM-G998U held a blurred page while reporting focus in dim room light (exposure × ISO about 272,000), and focused once the page was lit. The SM-G998U offers no boost: none of its cameras lists the low-light boost AE mode. The stats strip shows `boost unsupported`, `off`, `inactive` or `active`.
- In a dark scene (exposure × ISO at or above the auto torch's threshold) with no lit torch and no active boost, `zsl` and `latency` captures scan before the shot, at the page or the preview's centre. On the SM-G998U, continuous autofocus in a dim room held a blurred page while reporting focus, which also hid the page from detection, but a scan before the shot focused. No fixed delay follows the lock: the shot waits for frames exposed after it (four steady ones with motion checking, at least one without), and zero shutter lag saves only a buffered frame that reports the lock. Even after such a scan, zero shutter lag can return a frame from before it (see zero shutter lag above), so in a dark scene `zsl` binds `latency`, which exposes a new frame after the gate approves, while the torch mode is `off` and no boost is enabled and supported. A boost the camera refuses, as CameraX does above 30 fps, counts as none: the refusal re-evaluates the mode and is remembered for the next bind until a boost succeeds. Darkness must last a second at or above the dark threshold, and light a second under it, before the mode flips; each flip rebinds the camera, after any photo in flight. A second, lower threshold for light kept the mode stuck: a lit room on the SM-G998U read about 15,000, between the dark threshold and half of it. `zsl` also binds `latency` after a second of frames with exposure converged but white balance not: on the SM-G998U under the auto torch and a lamp, white balance searched for every frame, so the buffer took no new frame and every gated shot was rejected for light. Frames with exposure still moving are skipped so a camera start does not count. A lit torch (`on`, or `auto` once it decided to light) binds `latency` at once: white balance under the torch almost always searched on the SM-G998U, so following white balance cost a second and a restart after the press, about 3 s to a shot. An auto torch lit when the camera stopped counts as lit at the next bind, since it needs another dark second to relight; if it does not relight, the bind after that returns to `zsl`. Locking white balance would not help: the buffer requires it converged, not locked. A rebind for the light keeps the auto torch's decision, which a rebind otherwise resets; the stop carries that reason, and a light rebind deferred together with another keeps it. The way back is sticky: `latency` stays until the scene is neither dark nor searching white balance, and then waits for a bind that happens anyway, such as the camera's restart after each shot. Switching back at once made each page cost two blank previews in torch light, and `zsl` is the shot more likely to smear. The binding records which cause chose `latency`. In `latency` bound for the light, a press with no page found scans at the preview's centre: under the torch, continuous autofocus held a page too blurred to detect while reporting focus, and with the torch lifting the exposure the scene did not count as dark, so the capture waited for the page until it was rejected. CameraX also skips the buffer per shot while the flash mode is `on` or `auto`, without a rebind, but those modes may fire the flash.

## Document focus

- Continuous autofocus runs whenever no scan holds the lens, aimed at the central 30% of the frame, where the guide holds a page, by a CameraX metering action that locks nothing. Nothing follows the page: no scan when it arrives, no refocus requests. Focus never blocks inference or resets confirmation. One `FocusController` owns tap and capture scans; its snapshot generation changes on every scan's start, settle and release, and capture restarts its steady sequence on a new generation.
- The lens is never parked (autofocus off at a fixed distance) to wait for a page: a settings change takes 8 frames to apply (`REQUEST_PIPELINE_DEPTH` on the SM-G998U), so a parked lens reported focus on a page 0.57–0.77 s after confirmation, against a median 0.15 s with autofocus left on.
- Continuous autofocus can still report a focus reached before the page arrived, on the background or a hand; twice in 9 arrivals it took 0.5 s and 1.5 s to notice the page. A capture therefore counts only focus reached after the page's first detected outline; a page unseen for a second arrives anew. Each frame record carries when its focus was reached, so readiness and steadiness judge the same frame. When the newest frame's focus is stale and autofocus is not scanning, a `zsl` or `latency` capture starts one scan at the page, since autofocus may never rescan a page it already held in focus. A tap's lock is exempt: the user chose it.
- Scans: `quality` captures scan at the page, or the preview's centre without the guide or a detected page. A first scan starts only before the focus deadline. Any capture scan that settles without focus is retried from where the lens stopped, whatever triggered it and whether that trigger still holds (owning the lens ends a stale focus): once in any case, and again while any frame during the failed scan smeared past the capture blur limit. In dim light a scan from a background distance with the hand moving slightly gave up short of the page and the capture was rejected while the page then came into focus; a scan that fails with the camera still ends the retries, since the scene is too dark or flat. A capture's pending scan extends the focus and page waits, and once it settles they wait up to 500 ms for a frame exposed after it, so the page it brought into focus can be seen; a moving hand can keep a capture waiting; a tap scans where tapped, metering focus and exposure as CameraX's own tap-to-focus does, and holds the lens 5 s, but an overdue tap still waits for a shot in flight, and a shot in flight refuses taps. The scanner handles taps itself because CameraX reports its tap only after sending the scan, so a capture decision could still read the old focus; the scanner publishes the tap's ownership first. A capture that skips the gate starts no scan and waits only for a tap's scan in progress. CameraX runs a locking scan in single-shot autofocus (`AUTO`) before its trigger and restores continuous autofocus on cancel; releasing a scan cancels it and then aims continuous autofocus again, because the cancel also clears its regions. CameraX only queues the switch to `AUTO` and does not wait for a frame in that mode, so a trigger may still meet continuous autofocus mid-scan; on the SM-G998U such a trigger was held until the passive scan ended, or ignored while it kept hunting. Whether a tap during a passive scan still focuses is a hand check.
- A frame's scanning state extends a focus wait only while the frame is under 500 ms old, so stalled analysis cannot hold a shot; an owned scan still pending always does.
- Timings are measured on the SM-G998U only. Frame records arrived about 50 ms apart; scans took 0.6–1.6 s from a tap in ordinary light, but in dim light a capture scan outlasted the old 2 s limit and was rejected as the page sharpened. CameraX settles each scan itself, unsuccessful after 5 s, so the scanner's own limit is now a 6 s backstop for a result that never arrives. The 4 s focus wait, 1 s for light and steadiness, 5 s tap hold and 1 s page loss are product choices. Debug builds log `af state=`, `page arrived`, the focus scan lines and `maxRecordGapMs` to measure them.

## Adaptive detection

- Once a trusted model result locks the outline, flow carries it and inference pauses. The aim is to stay paused through normal handling, so speed never wakes inference: an earlier speed limit, then a tighter net-displacement limit, both woke it on ordinary hand tremor.
- Tracking fits a homography, because a page is flat and tilt is then modelled exactly. Tilt bends far tracks away from any similarity, so a loose similarity consensus seeds the homography, which is held to the strict tolerance.
- Inference wakes when:
  - tracking is lost. The estimator always replaces its reference frame, so one failed frame breaks the chain.
  - a page region loses its features. Features are reselected every frame, so a covered region soon reads clean again; flow cannot show recovery, so any loss requests a model confirmation. The guide stays trusted, so inference revalidates every 60 ms and one confirmation returns straight to the pause. Region loss never resets the policy by itself; only guide expiry does, when its configured hold deadline (400 ms by default) runs out.
  - any corner of the tracked outline strays more than 5% of the upright frame width from the confirmed outline (`scene changed`). Translation counts as well as tilt, because tracking error grows with distance from the confirmed frame.
- Focus does not wake it: focus decides whether a model result can be trusted, not whether flow holds.
- There is no periodic recheck while paused, so a change that preserves the tracked texture goes unnoticed until a wake condition.
- The thresholds are starting settings.
- The pacing policy is a small per-platform state machine fed by shared guide and flow evidence; `tests/fixtures/parity/adaptive.tsv` holds the sequences every platform must reproduce.
